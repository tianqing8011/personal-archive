AI AGENTS · COURSE NOTES

构建高效的 AI 智能体

从“回答问题”到“完成任务”：理解智能体的运行方式、能力边界与可靠部署。

核心主张：目标不是最大化自主权，而是在可控风险下，可靠地完成目标。

ONE-PAGE OVERVIEW

知识总览

本课程语境中的智能体： 使用大语言模型，根据目标和环境反馈选择下一步， 并通过工具采取行动的系统。
关键不是“能调用几个 API”，而是 能否依据结果调整行动，并判断何时结束或请求帮助。
AI 智能体 ├─ 1. 是什么？ │ ├─ 从生成回答，转向执行任务 │ ├─ 感知 → 推理 → 行动 → 观察 → 循环 │ └─ 自主程度：副驾驶 / 半自主 / 限定范围内自主 ├─ 2. 如何决策？ │ ├─ LLM：理解目标、选择步骤、解释反馈 │ ├─ 规划：任务分解 / 迭代改进 / ReAct │ └─ 纠错：验证 / 澄清 / 备选方案 / 停止与升级 ├─ 3. 如何连接世界？ │ ├─ 工具：搜索、文件、代码执行、API、浏览器 │ ├─ 记忆：会话记录、中间笔记、持久化信息 │ └─ 上下文工程：在恰当时间提供恰当信息 ├─ 4. 如何协作？ │ ├─ 协调者—工作者 / 流水线 / 独立审查 │ ├─ 消息传递 / 共享状态 / 结构化交接 │ └─ 权衡：收益 vs 协调成本、延迟、错误传播 └─ 5. 如何可靠落地？ ├─ 场景：编码、研究、业务流程 ├─ 防护：权限隔离、审批、沙盒、预算限制 └─ 评估：质量、成本、耗时、返工与风险
CHAPTER 01

①什么是智能体？

形态谁决定下一步？典型表现
固定工作流预设规则与分支按既定流程处理表单、发送通知
问答式助手主要由用户推动解释代码、起草内容、提出建议
智能体系统模型根据目标与反馈动态选择读取代码 → 修改 → 测试 → 根据错误修复

这是理解交互模式的简化框架，不是严格的产品分类。 同一个产品可以同时包含聊天、固定工作流和智能体功能。

运行机制：一个不断获得反馈的循环

接收目标 → 感知信息 → 推理决策 → 工具行动 → 观察结果 ↺

每轮都需要判断：目标完成了吗？是否需要更多信息？ 是否值得继续尝试？是否应交给人处理？

四个理解维度

  • 模型：负责理解、推理和决策。
  • 工具：决定能执行什么操作。
  • 记忆：保留目标、发现和执行进度。
  • 环境：文件、网页、数据库等感知与行动对象。

三个常见场景

  • 客服：查账户、核对交易、按授权处理问题。
  • 编码：理解仓库、修改代码、运行测试。
  • 研究：搜索资料、比较来源、生成报告。

这是三个例子，并非智能体只有这三类。

自主程度：不是越高越好

级别工作方式适合的情境
副驾驶AI 提建议，人决定是否执行不熟悉的任务、学习阶段、需要逐项审查
半自主常规步骤自主执行，关键动作审批有明确流程，同时存在高风险节点
限定范围内自主在事先规定的权限内完成任务任务明确、容易验证、失败影响可控

选择依据：操作是否可逆 × 失败影响多大 × 该任务上的实际可靠性。 “自主运行”不等于拥有无限权限。

  • Human-in-the-loop：关键行动前，由人批准。
  • Human-on-the-loop：系统运行，人持续监督并可干预。
CHAPTER 02

②智能体如何推理与规划？

LLM 是决策引擎，不是事实数据库，也不是执行环境。 它擅长处理语言、生成方案和整合信息； 精确计算、实时查询、实际操作应结合相应工具与验证机制。

三种任务推进方法

方法核心思路示例
自上而下规划先拆分目标，再按依赖关系执行调研 → 比较 → 草拟方案 → 验收
迭代改进先产生可评估结果，再根据反馈修改初稿 → 对照要求 → 修改 → 复核
ReAct推理与行动交替，边做边调整搜索 → 阅读结果 → 修正问题 → 再搜索

这些方法可以组合使用，不必三选一。

面对不确定性，使用四种机制

  1. 验证：检查证据、运行测试、读取真实执行结果。
  2. 澄清：缺失信息会明显影响结果时，向用户提问。
  3. 替代：失败后调整关键词、工具或方案，而非机械重试。
  4. 停止与升级：达到重试、时间或费用上限后暂停并报告。
最危险的失败不是报错，而是“看起来成功”。 报告可能文笔流畅但引用错误，代码可能测试通过却没有满足需求。 验收应围绕任务目标与证据，而不是语气和格式。

关于逐步推理： 将复杂问题分解有助于检查过程，但解释得详细不代表结论必然正确。 应优先查看可验证的依据和中间结果。

CHAPTER 03

③工具、记忆与上下文

工具调用：模型提出请求，系统负责执行

判断需求 → 选择工具和参数 → 系统校验并执行 → 返回结果 → 再决策

工具可以是搜索、文件读写、代码执行、数据库查询或浏览器操作。 函数调用通常以结构化参数表达请求，便于程序解析。

三个不能混淆的层次： 输出了调用请求 ≠ 工具已执行； 工具已执行 ≠ 执行成功； 执行成功 ≠ 用户目标已实现。

记忆：区分当前可见与长期存储

类型主要用途示例
会话 / 短期记忆维持当前任务的连续性用户要求、对话记录、工具返回
工作记忆保存中间发现与进度任务清单、研究笔记、部分草稿
长期记忆跨会话保留可复用信息偏好配置、持久化笔记、知识库
  • 上下文窗口：模型单次调用可使用的信息范围，容量通常以 token 衡量。
  • 持久存储 ≠ 当前可见：保存过的信息，仍需被检索或载入上下文才能供本次使用。
  • RAG：先检索相关材料，再将其提供给模型生成答案；不等于重新训练模型。

上下文工程：不是“塞得更多”，而是“给得更准”

应该保留

  • 目标、验收标准、权限边界。
  • 相关证据及其来源。
  • 已完成步骤与关键决定。
  • 待解决问题和不确定性。

应该控制

  • 无关文件和重复工具输出。
  • 过期假设、旧版本方案。
  • 冗长但无新增信息的历史。
  • 与当前任务无关的背景。

操作口诀：筛选 → 摘要 → 保留来源 → 按需检索。 切换任务时可以减少无关上下文，但应保留仍然相关的结论与约束。

注意：上下文满了如何处理，取决于系统的截断、摘要或报错机制； 不是所有模型都会自动“忘掉最旧内容”。会话记录是否保留也取决于产品实现。

CHAPTER 04

④多智能体系统

先做好一个智能体，再考虑多个。 先检查工具、提示、上下文和流程是否足够， 不要用增加角色数量代替解决基础问题。

四种常见组织方式

模式工作方式主要风险
协调者—工作者统一拆分任务，分配执行，再整合分工错误、交接遗漏、汇总失真
流水线研究 → 写作 → 编辑等顺序交接早期错误被后续加工放大
独立解答 / 辩论分别处理同一问题，再比较结论共同偏差、无效争论
执行—审查一个完成工作，另一个审核审核者重复同样的错误

协作依靠什么？

  • 消息传递：发送任务、结果、反馈。
  • 共享状态：共同使用文件、数据库或任务看板。
  • 结构化交接：统一输入、输出和验收格式。
推荐的交接内容

子任务目标｜必要背景｜输入材料｜输出格式｜证据来源｜未决问题｜验收标准

何时值得用多个智能体？

  • 子任务可以独立处理，并行有明确收益。
  • 不同任务需要不同工具、权限或上下文。
  • 需要相对独立的审查与验证。
  • 单次上下文无法有效容纳整个问题。
多份一致答案不等于独立证据。 多个智能体可能使用同一模型、同一错误来源。 应检查证据和错误的独立性，而不是简单投票。 多智能体也不一定更慢：并行可能缩短耗时，但协调开销和总费用可能增加。
CHAPTER 05

⑤实际应用、安全与部署

场景主要价值验收重点
编码修改、测试、调试等步骤形成反馈循环需求是否满足、测试覆盖、安全与副作用
研究分析加快资料收集、比较和结构化整理来源真实性、时效性、引用是否支持结论
流程自动化串联工单、数据、通知和内部系统权限、异常处理、重复执行与状态一致性

两类关键风险

  • 目标偏离： 系统优化了表面指标，却没有实现真实意图。 例如通过少记录投诉来“减少投诉”。
  • 提示注入： 网页、邮件或文档中的恶意内容试图让系统偏离原任务。 外部材料应被当作待处理的数据，而不是天然可信的指令。

防护应嵌入系统，而不只是写在提示词里

行动边界

  • 最小权限：只提供任务必要的能力。
  • 隔离执行：优先使用测试环境或沙盒。
  • 敏感操作前审批：发送、支付、删除、发布。
  • 保护敏感数据，限制外传路径。

运行约束

  • 设置调用次数、时间和费用上限。
  • 记录操作过程，便于追踪和审计。
  • 提供停止、恢复和人工接管机制。
  • 检查工具结果和最终交付物。
不要把防护当成绝对保证。 输入过滤不能彻底解决提示注入；沙盒仍需要正确配置； 人工审批也可能因信息不足或频繁弹窗而失效。

理解课程中的未来展望

更强的推理、持久记忆、更可靠的工具调用，以及专业化协作， 是课程讨论的发展方向，而不是所有产品已经具备的能力。

值得培养的能力： 清晰描述任务、组织上下文、设计流程、验证结果，以及领域专业知识。

PUT IT INTO PRACTICE

实践：从一次可验收的小任务开始

以下为根据课程整理的实践模板，便于将概念转成实际操作。

1. 给智能体的任务说明模板

【目标】 需要解决什么问题？最终交付什么？ 【材料与上下文】 可以使用哪些文件、数据和来源？ 哪些资料最重要？有哪些已知事实？ 【成功标准】 怎样判断完成？需要哪些证据或测试？ 【权限边界】 允许读取、修改什么？ 哪些操作必须经过我确认？ 【运行限制】 时间、费用、重试次数上限是多少？ 【不确定性处理】 缺少关键信息时先提问。 无法核实的内容明确标注。 遇到权限限制或连续失败时停止并报告。 【最终输出】 交付物 + 验证结果 + 未解决问题 + 需要人工确认的事项。

2. 启动前检查清单

  • 目标是否具体，验收标准是否可检查？
  • 固定脚本或单次问答是否已经足够？
  • 所需工具和数据是否真实可用？
  • 是否只授予完成任务所需的权限？
  • 是否明确了敏感操作的审批节点？
  • 是否限制重试、耗时与费用？
  • 失败后是否能够停止、恢复或交给人？
  • 是否保留了核查结果所需的证据？

3. 评估时不要只看“成功率”

维度应该问什么？
质量是否达到预先定义的验收标准？
成本模型、工具、重试和人工返工共花费多少？
效率从开始到获得可用结果，总耗时多久？
风险失败可能造成什么损失？能否及时发现？
可控性是否遵守权限，能否暂停和追踪操作？
建议的入门练习： 让一个只读智能体根据指定的三份文档生成对比表。 要求每条结论注明出处，缺失信息标注“未找到”，不允许外部发送或修改原文件。 观察它如何选择资料、使用工具、处理分歧与验证结果。
GLOSSARY & CAUTIONS

术语速查与易错点

术语一句话理解
Agent / 智能体围绕目标，根据反馈选择并执行行动的系统。
LLM / 大语言模型处理语言与上下文，并承担推理和决策的模型。
Agent loop / 智能体循环感知、推理、行动、观察的反复过程。
Tool calling / 工具调用模型提出结构化请求，由外部系统执行工具。
ReAct让推理和行动交替推进的模式。
Context engineering / 上下文工程组织模型当前需要的信息，控制无关信息。
RAG / 检索增强生成先找相关资料，再结合资料生成输出。
Embedding / 嵌入将内容表示为数值向量，以支持相似性检索等操作。
Orchestration / 编排组织任务分工、执行顺序、交接与整合。
Handoff / 交接转移任务控制权及必要上下文。
Prompt injection / 提示注入通过输入中的恶意指令干扰系统原定行为。
Guardrails / 护栏限制权限、行为和输出的多层防护措施。

阅读原课程时，特别注意这些边界

  • 能用工具，不自动等于智能体：还要看谁决定流程及如何适应反馈。
  • 自我纠错不保证成功：固定自动化也能重试和处理预设异常。
  • 可靠性不能脱离任务风险：99% 成功率不自动意味着可以完全自主。
  • Git 不能撤销一切：外发邮件、泄露数据和线上副作用不等于代码修改。
  • 上下文不是唯一瓶颈：模型、工具、权限和任务设计都可能造成失败。
  • 研究可以部分自动核查：但来源存在，不代表它支持报告中的结论。
  • 责任归属不能一概而论：课程的问责讨论不能替代具体情境下的法律判断。
最后记住：明确目标 · 提供正确上下文 · 控制权限 · 验证结果 · 知道何时停止
