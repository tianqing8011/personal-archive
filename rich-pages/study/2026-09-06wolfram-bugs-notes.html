01全文主线：规则、预期与反例

可以把整篇文章读成一个问题：当一套规则被真正运行起来， 它是否始终符合我们对它的简洁描述？

定义预期→ 运行规则→ 发现偏离→ 寻找保证

第一段：建立问题

用简单计算模型讨论正确性、规格与隐藏缺陷。

第二段：寻找保证

比较运行测试、观察内部结构与构造形式证明。

第三段：讨论边界

引入计算不可约性，追问经验归纳为什么可能失效。

第四段：回到实践

借助规则学与数学案例，讨论语言、可观测性和 AI。

02什么才算 Bug？

作者观点 · 概括

判断程序有没有 Bug，需要先说清楚它应该做什么，或者不应该做什么。 单看规则是否被执行，无法判断规则是否实现了我们的目的。

“运行正确”和“满足要求”不是同一件事

一个程序可能严格执行了写下来的指令，却输出了不符合需求的结果。 此时出错的不是机器执行规则这件事，而是实现与要求之间的关系。

规格也不一定要求一个精确输出：它可以要求终止、限制资源， 或要求所有可达状态都满足某个安全条件。

在约定的输入与环境范围内：
正确性要求 = 所有允许的执行行为都满足规格 S
理解边界

“需要判断标准”不等于“没有书面规格就没有 Bug”。 判断标准也可能来自用户需求、接口契约或合理的隐含要求。 形式化只是让这些标准更明确。

同一种偏离，在不同语境中的名字不同

  • 规则学：行为突破观察者的猜测，构成意外。
  • 数学：某个对象不满足普遍猜想，构成反例。
  • 软件：实现违反适用要求，构成缺陷。

这些现象具有相似结构，但不能完全画等号。 意外不一定是错误，错误也不一定让人感到意外。

对应原文：[1] What Counts as a Bug? 定义边界为本笔记补充。

03测试、理解与证明分别回答什么？

方法主要问题不能直接推出什么
运行测试 这些输入、时序和环境下发生了什么？ 未覆盖情况也全部正确。
内部观察 哪些状态与机制产生了结果？ 看到的模式永远成立。
形式证明 在明确假设下，命题是否由模型推出？ 模型、规格和部署环境必然一致。

证明不只是“做了更多测试”

测试可以逐个检查实例；证明则可能找到一个覆盖全部允许实例的结构。 原文既讨论证明搜索的困难，也展示了对简单机器的普遍正确性证明。

若干实例成立 ≠ 普遍命题已证明
基础情形 + 有效的归纳步骤 ⇒ 对相应范围的普遍保证

预测结果与证明性质必须分开

对某个输入立即说出排序结果，和证明排序程序的输出有序、元素不丢失， 是不同任务。知道一个程序满足规格，不要求事先写出每次执行的全部细节。

讨论中的重要修正

证明搜索可能没有通用的终止保证，不等于证明没有实际优势。 也不能把“没有找到证明”当成“命题为假”，或当成“命题不可证明”。

对应原文：[1] But What about Formal Proofs? 方法对照与排序例子来自学习讨论的整理。

04计算不可约性：不能任意跳过的计算

作者观点 · 概括

对某些计算行为，预测本身需要付出不可省略的计算工作； 简短规则未必给我们一条获得长期结果的同样简短的捷径。

它解释的是预测困难，不自动证明缺陷必然存在

Wolfram 用计算不可约性解释为什么简单系统也可能反复突破预期。 但从“行为难以完整预测”到“违反指定规格”，还隔着一步： 我们关心的性质是否恰好仍可被证明或约束？

难以预测全部细节 ⇏ 一定违反规格
内部行为复杂 ⇏ 无法证明任何性质

“计算可约口袋”怎样理解？

在作者的框架里，即使整个过程难以概括，某些方面仍可能有简洁规律。 我们可以不追踪每个内部细节，却证明某个边界不会被越过。

因而，可约性应结合所问的问题理解： 预测完整状态、判断终止、验证不越界，并不是同一项任务。

术语防混淆

本笔记不把“计算不可约性”“混沌”“看起来随机” 和“目前不知道如何分析”当成同义词。 图案不规则本身，不足以证明一个严格的不可约性结论。

同样，作者关于不可约性广泛存在的判断，应保留其计算等价原理背景， 而不是改写成“任何有用程序都必然有 Bug”的定理。

对应原文：[1] Computational Irreducibility and Bugs。

05有限观察：有价值，但不是无限保证

测试很多次都成功，容易使人把“观察到的稳定模式”升级成“永远成立的规律”。 本文反复警惕的正是这一步跳跃。

P(x₁), P(x₂), …, P(xₙ)
一般不能仅凭这些实例推出 ∀x，P(x)
适用范围

这里说的是尚未穷尽的输入或行为范围。 如果问题本身有限，且已确实穷尽所有相关情况， 穷举也可以建立该范围内的保证。

测十次与测一亿次当然不等价

两者可能都不足以证明无限范围内的正确性， 但在覆盖面、发现反例的机会和统计证据上可以差别很大。 测试价值还取决于输入分布、案例多样性及是否覆盖关键边界。

一个帮助理解的概率模型

作为学习补充，假设每次测试独立、来自同一个固定分布， 每次触发失败的概率均为 p，那么 N 次全部漏掉失败的概率为：

Pr[没有发现失败] = (1 − p)N

这说明增加测试可以有价值；同时也提醒我们： 当 p 未知、输入存在相关性或分布发生变化时，不能直接套用这一简化模型。

经验归纳不等于数学归纳法

  • 经验归纳：从观察过的情况，推测未观察情况。
  • 数学归纳法：证明基础情形与递推步骤，建立普遍结论。

因此，“规则学归纳可能失败”不是在否定数学归纳法。 它也不意味着自然科学中的经验研究或概率推断失去意义。

对应原文：[1] Did I Test Enough Cases? 概率式为本页明确假设下的学习推导。

06五类规则学意外

以下按“改变什么，才发现意外”整理讨论中的案例。 这是一种学习分类，不是原文给出的正式分类体系。

探索维度此前的预期原文案例
规则空间 简单规则只产生简单行为。 Rule 30 展示出明显不规则的复杂图案。
输入空间 固定规则的行为种类已经看全。 三色元胞自动机在初始条件编号 916、97,439 等处出现新行为。
运行时间 增长这么久，应该不会停了。 组合子表达式在 137,356,329 步后停止。
宏观形态 近圆形增长会一直维持。 二维元胞自动机约 3,000 步后出现“喙”状突出。
执行路径 每次增长后都能继续增长。 多路生长系统在 9 步后出现无法继续扩展的特殊簇。

怎样把案例转化为工程问题？

  • 输入：有没有普通样本之外的边界输入或状态组合？
  • 时间：长期运行是否会触及资源或计数器阈值？
  • 形态：平均指标是否掩盖了局部异常？
  • 路径：是否存在某种调度或操作顺序触发失败？
类比不是因果证明

这些工程问题与规则学案例在结构上相似， 不代表资源耗尽、溢出或死锁都由计算不可约性造成。 许多具体故障可以通过普通机制分析直接解释。

三个需要保留的限定

  1. 长期运行才停止，不证明该具体例子不存在更快的分析方法。
  2. 少数路径到达死端，不等于所有路径都失败，也不自动给出失败概率。
  3. 意外行为只有违反要求时，才构成工程意义上的 Bug。

案例依据：[1] Some Typical Ruliological Surprises。 数值采用原文报告；本页未独立复算这些实验。

07数学中的“Bug”：错的是猜想

数学对象不会突然停止遵守定义。所谓数学“Bug”， 在这些案例里指的是对象突破了人们从有限实例形成的猜想。

案例一：多项式因式的系数

讨论 xn − 1 的有理数域上首一不可约因式时， 小规模案例容易让人猜想：系数只能是 −1、0、1。 到 n = 105，相应圆分多项式中出现了绝对值为 2 的系数。

记忆要点

讨论的是分解所得因式的系数， 不是说 x105 − 1 本身出现了一个新的系数。

案例二：素数竞赛的领先反转

原文比较形如 3m + 2 与 3m + 1 的素数累计数量。 前期图像呈现出很强的领先趋势； 但原文报告，到第 23,338,590,792 个素数时， “前者数量减去后者数量”的累计差变为负数。

注意这个数字是素数的序号，不是那个素数本身。 本页用它说明长期偏向不等于永不反转，不把有限图像解读成严格正值定理。

长期成立的统计趋势 ≠ 对所有位置成立的不变量

数学里至少有三种不同的失误

  • 猜想错误：声称的普遍命题本来就是假的。
  • 证明错误：某一步推理并不成立。
  • 形式化错位：证明了形式命题 T，却没有表达真正想问的 T*。

关于“数学位于可约口袋”的判断

Wolfram 认为，人类数学活动偏向可理解的结构， 因而倾向于选择能够获得可管理证明的问题。 本笔记把它保留为作者的解释框架，而非有关全部数学实践的既定定理。

对应原文：[1] Mathematical “Bugs”。 三层失误分类为讨论整理；实验数值未独立复算。

08回到工程：不是放弃保证，而是说清保证

1. 高层抽象：减少需要亲自协调的机制

作者强调语言原语与人类意图之间的匹配。 例如，直接表达“排序”，而不是每次重新编写底层操作， 可以减少应用代码中需要自己管理的细节。

但这种封装不自动证明整个系统可靠： 用户仍然依赖原语语义、库实现、运行时及其组合方式。 作者对 Wolfram Language 的具体评价，应与一般性的抽象设计思想分开阅读。

不要把短小当作正确性证书

短代码可能减少重复逻辑，也可能只是把复杂性藏进调用中。 值得追求的是清晰的语义和更少的隐含假设，而不只是更少的字符。

2. 内部可见：从结果走向机制

原文强调观察计算内部。讨论中可以把这一点延伸为： 记录关键状态、转换原因与执行路径，而不只记录最终报错。

观察过程→ 提出机制假设→ 设计反例测试→ 证明关键性质

图像、日志与追踪可以帮助理解，但视觉确信不是自动证明。 展示有限时间、压缩状态或遗漏路径，都会限制观察能支持的结论。

3. 人为失误与复杂交互：有区别，也可能重叠

原文区分常见人为错误模式与更深层的计算意外。 实践中不宜把二者理解成互斥分类： 一个普通的边界条件错误，也可能只在极复杂的交互历史中暴露。

4. AI：训练达标不是所有情境下的保证

作者把训练得到的神经网络描述为难以用人类可理解机制完整解释的计算体。 讨论中最值得保留的结论是： 在训练或评估样本上表现良好，不能单独推出对所有输入与交互历史都可靠。

避免两个极端

不能把幻觉全部归因于计算不可约性，也不能从语义行为难以预测， 推出任何约束都无效。权限、资源及工具接口可以单独设计与验证， 但具体保证仍取决于实现和威胁模型。

5. 近似计算：首先明确误差契约

原文讨论了在低层程序空间中，容许某些偏差可能换取更短程序的权衡， 同时明确指出：在原语贴合任务的高级语言中，这种缩短未必出现。

学习时还应分清“允许近似”与“允许违约”。 如果规格本来就允许一定误差，那么在约定范围内的近似结果不天然是 Bug。

相对于分布 D 的示意要求：
Pr[p(x) = f(x)] ≥ 1 − ε

这里只是某一种允许失败概率的规格示例。 确定性近似算法也可以采用最坏情况误差界，不必使用上述概率形式。

工程延伸 · 本笔记的行动框架

明确需求 → 选择清晰抽象 → 建立内部可观测性 → 搜索反例 → 证明关键性质 → 设计隔离与恢复。

作者观点对应：[1] Bugs in Practice。 行动框架与保证边界是学习讨论的重构，不是原文逐字方案。

09四层分析框架：偏差究竟发生在哪里？

以下是学习讨论提出的定位工具，不是作者正式定义的“四层理论”。 它帮助我们避免把所有问题都归结为计算不可约性。

① 意图 → 规格

写下来的要求，是否准确表达真正的需要？

② 规格 → 实现

代码是否在规定条件下满足这些要求？

③ 观察 → 行为范围

已测试的情况，究竟覆盖了哪些输入、时序和状态？

④ 模型 → 运行环境

验证时假定的环境，与实际运行条件是否一致？

为什么不用简单的“不等号”定义这四层？

规格和程序是不同类型的对象，不能仅用“规格 ≠ 程序”来定义错误； 应当问“实现是否满足规格”。 同样，环境变化导致输出变化也不必然是 Bug， 因为规格可能本来就允许这种变化。

本笔记的定位

规则学视角最有启发性的地方，是提醒我们： 已见行为可能只是完整行为的一小部分。 但“覆盖不完整”是一种知识局限，本身还不是缺陷存在的证明。

来源：本次学习讨论的分析性重构；概念背景见 [1] What Counts as a Bug? / Did I Test Enough Cases?

10容易误读的地方

容易滑向的说法本笔记保留的边界
所有有用程序必然有 Bug。 预测困难不自动推出违反指定规格。
不可约性就是混沌或随机。 这些概念不能仅凭直觉或图像互相替代。
测十次和测一亿次一样。 都可能不是普遍证明，但证据强度与覆盖范围不同。
运行很久才停止，说明没人能提前分析。 一个运行结果不构成对所有分析方法的下界证明。
有形式证明，程序就没有计算价值。 证明输出满足规格，不等于无需计算就知道具体输出。
短程序的行为一定容易理解。 描述长度、运行时间和行为结构复杂度需要区分。
看到内部运行图就能确信永远正确。 观察帮助提出结构性解释，不能自动覆盖全部情况。
近似算法就是容忍 Bug。 允许范围内的近似与违反误差契约不是同一件事。
不同环境输出不同就是 Bug。 还要检查环境是否在约定范围，以及输出是否违反要求。
所有安全异常都是漏洞。 需要结合安全要求、威胁模型和实际影响判断。
关于原讨论中的复杂度公式

本版不沿用“K(P) 很小，所以 K(H) 仍可能很大”来说明简单规则产生复杂行为。 若 K 指通常的 Kolmogorov 复杂度，还必须计入输入、运行长度等描述条件。 本页只保留不混用复杂度概念的自然语言结论。

本节是对学习讨论中措辞和推理边界的校订，不是原文的独立章节。

11复习：我真正应该记住什么？

一分钟回顾
  1. Bug 的判断离不开适用的需求或规格。
  2. 简单规则也可能产生超出直觉的行为。
  3. 有限测试有价值，但通常不是未覆盖范围的普遍证明。
  4. 不能完整预测，不等于不能证明关键性质。
  5. 抽象与可观测性帮助理解，不能替代明确的保证条件。
  6. 工程目标不是知道每个细节，而是让重要承诺有依据。

先想一想，再展开答案

1. 为什么 Rule 30 的复杂图案本身不是软件 Bug？

它只说明行为超出了某种直觉。除非该行为违反事先适用的要求， 否则不能仅凭“不规则”或“出乎意料”把它定义为缺陷。

2. 测试更多次究竟有什么用？

可以增加覆盖、发现反例并提高特定假设下的统计信心。 但样本数量不能替代对输入分布、边界条件和未覆盖范围的分析。

3. 程序内部很复杂，还能证明它安全吗？

可能。关键是“安全”具体指什么，以及是否能找到覆盖该性质的不变量、 抽象模型或其他论证；无须预先知道所有内部细节。

4. 数学归纳法为什么不受“有限样本不能证明全部”直接否定？

因为它不仅检查基础实例，还证明从任意一个适用实例到下一实例的逻辑步骤。 普遍性来自已证明的结构，而不是来自样本很多。

5. 为什么“允许 1% 错误”还不是一份完整规格？

还要说明错误的定义、输入分布、统计范围、哪些情况不可失败， 以及如何验证这个承诺。平均错误率不能自动代表所有风险都可接受。

6. 这篇文章最值得带回日常编程的一个问题是什么？

“我现在的信心究竟来自哪里？” 是熟悉感、有限测试、机制理解、明确证明，还是对某个库或环境的信任？ 把信心来源分开，才能找到下一步应补的证据。
