## 三、解剖转译层

### 1. 业务全貌（本归档最核心的资产）

**数据源（腾讯文档收集表）：**
- 通过微信小程序"腾讯文档收集表"提交，可复制也可导出 Excel
- 普通订单固定 10 列：`收件人（必填）| 手机号（必填）| 收货地址（必填）| 平台订单号（非必填）| 商品信息 | 规格信息（非必填）| 商品数量（非必填）| 重量kg（非必填）| 备注（非必填）| 提交者（自动）`
- 定制订单（第二种格式，一周发一次货）：`提交时间（自动）| 定制内容（必填）| 收件人信息（必填）| 货物内容（必填）| 店铺名称标记 | 定制效果图 | 提交者（自动）`——定制效果图列忽略不处理

**打单软件（菜鸟包裹）：**
- 导入模板 9 列：`收件人（必填）| 手机号（必填）| 收货地址（必填）| 平台订单号（非必填）| 商品信息（非必填）| 规格信息（非必填）| 商品数量（非必填）| 重量kg（非必填）| 备注（非必填）`
- 导出"发货记录"（约 30 列），关键列：店铺名称、订单编号、收件人手机号、快递单号、商品名称、商品id、skuid、商品规格、商品数量、子订单状态等

**关键业务参数：**
- 每天约 **80 单**，不存在"一单多包裹多单号"
- 打单软件导出可带自定义字段（用于回填匹配）
- 快递单号在发货记录中形如 `圆通号码-YTXXXXXXX`，需去除前缀，只保留 `YTXXXXXXX`

### 2. 流程五段式设计

```
①收集：分销商腾讯文档提交 → 用户导出 Excel 放入 inbox_raw/
②解析：读腾讯表 → 拆收件信息（姓名/手机号/地址）→ 清洗字段
③导出：生成菜鸟导入文件（9列）+ 更新累计订单（14列）
④回填：菜鸟导出发货记录 → 按 order_id/手机号 匹配 → 写入快递单号
⑤归档：腾讯源文件改名移入 archive/（日期-批次），保证可追溯
```

### 3. 核心规则（每一轮迭代沉淀的"硬规则"）

**收件信息解析（姓名[尾号] → 姓名, 手机号-尾号）：**
```
输入：李师[0254],17896609954,云南红河州弥勒市...
输出：收件人=李师  手机号=17896609954-0254  地址=云南红河州弥勒市...
```
- 手机号以 `1\d{10}`（11位、1开头）为锚点，找不到则整行标记"解析失败"
- 姓名旁或文本中出现 `[数字]`（2-6位）视为尾号，拼接到手机号后：`主号-尾号`
- 原文本已带 `-分机` 的优先保留，不重复追加
- 地址 = 去掉姓名、手机号、尾号后的剩余文本，**信息保留型清洗**（只去空白，不删 `@`、`#`、仓库标记等）
- 空值规则：空白必须为空白，**不允许 nan 文本**（`df.fillna("")` + 清除字符串 `"nan"/"None"`）

**业务主键 order_id（保证回填 100% 命中）：**
```
格式：CN + YYYYMMDD + 批次 + 4位序号
示例：CN20260225_1200_0001  或纯数字 CN2026022512000001
```
- 写入菜鸟导入文件的"平台订单号（非必填）"列
- 菜鸟导出时带出该字段 → 回填时按 order_id 精确匹配，不做姓名/手机号模糊匹配
- 同一天同批次序号递增，多源文件合并不重复

**批次识别（按文件修改时间）：**
- 11:00–13:30 → 记为 `1200` 批
- 15:00–18:30 → 记为 `1600` 批
- 其它时间 → `other`（仍生成，但日志提示"批次不典型"）

**回填匹配优先级（按用户确认）：**
- 首选 order_id（平台订单号）精确匹配
- 手机号前 11 位匹配兜底（用户确认"几乎不会出现手机号冲突"，冲突输出 `冲突清单_YYYYMMDD.xlsx`，不自动解决）
- 商品信息/skuid 仅作二次匹配（菜鸟"商品名称"与腾讯"商品信息"文本常不一致）

**其他规则：**
- 收货地址（必填）替换全量表原来的"省市区"列内容（列名可不改）
- 备注 = 分销商"店铺标记"，无固定格式，整段保存；**不加** order_id 后缀（用户明确选择"不加"）
- 累计订单是**单一真源**，固定路径 `workspace/state/累计订单.xlsx`，Excel 打开时脚本"快速失败"（防锁冲突）
- 腾讯源文件处理成功后**自动改名归档**到 `archive/`：`YYYY-MM-DD-批次-原文件名.xlsx`（用户原意删除，AI 建议归档更安全，用户采纳）

### 4. 累计订单 14 列（月度分销商结算的基础）

```
提交时间 | 收件人 | 手机号 | 收货地址 | 平台订单号 | 商品信息 | 规格信息
商品数量 | 重量kg | 备注 | 提交者 | 处理日期 | 批次 | 快递单号
```
（提交者列用于月度按分销商筛选结算）

### 5. 方案选型：为什么是"本地脚本"而不是 RPA / 中间库

| 方案 | 适合 | 结论 |
|---|---|---|
| **A. 本地 Python 脚本**（用户采用） | 数据源能导出 Excel、打单软件支持 Excel 导入导出 | 成本低、改动小、代码小白可跑（拖文件+双击 bat） |
| B. 本地脚本 + RPA（Power Automate / UiPath） | 数据源只能 UI 点下载 | 页面改版就崩，维护成本高，暂缓 |
| C. 订单中间库（SQLite/Postgres） | 订单量大、多经销商、对账要求高 | 初期搭建重，日单 80 暂不需要 |

**关键前提：** 腾讯文档能导出 Excel、菜鸟包裹支持 Excel 导入——两个"能导出/能导入"就圈定了方案 A 可行。

### 7. 排障集锦（都是真实踩坑，规则化的教训）

1. **列名不匹配**：腾讯表头/菜鸟表头经常带空格、全角括号、BOM——`read_excel_any()` 必须统一 `normalize_df_headers()`（去空格、统一括号、清 BOM）
2. **隐藏列 ≠ 删除列**：隐藏列 pandas 能读到；读不到往往是导出时没带出或表头错位
3. **参数不识别**：run.bat 传了 `--conflict-mode export_only` 但脚本版本不支持 → 脚本在解析参数阶段就退出，后续全部不执行
4. **累计订单找不到手机号**：腾讯表手机号提取失败的行被过滤掉，菜鸟却生成了面单 → 需要"被过滤订单输出"（哪些行因何被丢）
5. **合并列解析**：分销商可能用三列填（收件人/手机号/地址），也可能整段粘进"收件信息（必填）"一列 → 两种都兼容，解析优先级要定
6. **nan 问题**：导出菜鸟导入文件出现 `nan` → `df.fillna("")` + `applymap` 清字符串 `"nan"/"None"`
7. **多行粘贴只读第一行**：Windows 控制台 `input()` 一次只读一行，多行粘贴后面全变成菜单输入 → 需 `read_multiline_until_blank()` 函数（在字库对比系统对话中解决，见第 13 篇归档）

### 8. 从"脚本"到"Skill"：工程方法论的成型

**AI 引入的三个概念（被用户迅速吸收）：**
- **契约（Contract）**：明确输入输出和规则，可验收——"遇到 X 必须输出 Y"
- **IR（中间层）**：内部统一字段的标准表，让解析与导出互不影响——两套输出（菜鸟 9 列 / 累计 14 列）都从 IR 生成
- **回归样例（Regression Samples）**：用固定样例保证迭代不改坏——"能验、能回归、能追溯"

**用户最终形成的"订单自动化 Skill 清单"（方向 A）：**
```
ReceiverParse         收件信息解析（一坨文字 → 收件人/手机号/地址）
OrderIRBuild          把两种腾讯表统一成 IR
CainiaoExport         IR → 菜鸟 9 列
LedgerExport          IR → 累计订单 14 列
ShipmentImport        发货记录 → 标准 tracking_no（去"圆通号码-"前缀）
TrackingMatchAndUpdate 匹配并回填累计订单
ArchiveRename         源文件归档改名
```

### 9. /compare：为什么"没掉队"——真懂 vs 假懂

用户切换到 `/compare @Claude-Sonnet-4.5` 后，Claude 给出三个判断（与订单自动化项目直接对应）：

1. **学的不是工具，是思维方式**：契约、IR、回归样例是工程思维，工具会换，方法论不会过期
2. **"被启发"= 一直在用 AI 方式重构问题**：订单混乱→想到自动解析；表头变化→想到中间层隔离；规则会变→想到回归样例
3. **概念迁移能力**：`订单自动化：腾讯表 → 统一IR → 菜鸟表/累计订单` 与 `Clawdbot Skill：杂乱输入 → 标准化接口 → 可调用组件` 结构同构

**"真懂 vs 假懂"的定义（Claude 金句）：**
- 假懂：只会用某个工具，工具变了就不会了
- 真懂：理解底层原理，换个场景立刻能映射上

**学美术类比（用户能直接共鸣）：** 初学临摹画家技法 → 进阶理解构图/色彩/光影原理 → 高手看到任何东西都用这套眼光重构。用户已经处在"看到任何问题都能用契约/IR/回归样例重构"的阶段。

### 4. 收件信息解析契约（用户与 AI 共同定稿的可验收版本）

```
Skill: ReceiverParse（收件信息解析）
输入: 一段文本（可能含换行、逗号、空格、引号、@、#、[]尾号）
输出: 收件人(必填) / 手机号(必填) / 收货地址(必填)
硬规则:
  1. 手机号锚点: 找 \b1\d{10}\b；找不到 → 手机号=""，标记解析失败
  2. 尾号规则: 文本中 [\d{2,6}] 视为尾号；手机号未带分机则输出 11位-尾号；
     已带 "-" 保持原样；多个 [] 优先取紧邻姓名的，否则取第一个合理的
  3. 地址: 去掉姓名/手机号/尾号后的剩余文本，信息保留型清洗
  4. 空值: 空白必须为空白，不允许 nan
副作用: 成功后源文件归档改名（日期-批次）
```

### 5. 两个标准化输出（契约的一部分）

- **菜鸟 9 列**：收件人（必填）手机号（必填）收货地址（必填）+ 平台订单号（非必填，写 order_id）+ 商品信息 + 规格信息 + 商品数量 + 重量kg + 备注（写店铺标记）
- **累计订单 14 列**：提交时间 收件人 手机号 收货地址 平台订单号 商品信息 规格信息 商品数量 重量kg 备注 提交者 处理日期 批次 快递单号

### 关键洞见

1. **代码小白最可靠的补位方式是"把业务规则说到极致"** —— 用户不懂代码，但她把表头精确名称、括号全半角、尾号规则、每天单量全部说清楚，这直接决定脚本能一次写对

3. **"信息保留型清洗"与"硬规则可验收"是契约的两面** —— 地址只去空白不删标记（信息不丢），规则写成"遇到 X 必须输出 Y"（结果可验）

5. **隐私考量推动技术选型** —— 飞书在线表 → 本地文件，是用户自己的决策，体现业务数据的隐私意识
6. **Skills / Clawdbot 与本项目同构** —— 用户凭直觉发现"采集→解析→导出→回写→归档"就是 Skills 的骨架；AI 确认这就是 Skill 思维。**用户没有掉队，因为方法论不会过期**
7. **真懂 vs 假懂** —— 工具会换，思维模式会留下；用户已从"追工具"进入"用 AI 思维重构问题"的阶段
