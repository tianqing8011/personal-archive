**日期：** 2026-05-21
**类型：** 电商业务 × 工具开发（可复用框架 / HTML 单文件应用 / RL 训练排障）

## 一、会话定位层

**这段对话在讲什么：** 用户正式开展"销售招募"业务——招募了一名销售人员，已指导其开好淘宝店铺，现在第一步是"教他上传第一款商品"。产品是**魔术臂章定制**（国家电网 / 山东吉林河北 / 建筑 / 应急救援场景）。AI 一开始给出了完整的产品上架指南（标题优化、SKU、FAQ、发货时效），但被用户纠正——**"你只需要给我框架即可，细节我自己填写，每个产品的框架可以串联在一个系统里"**。于是整个下午围绕"一套可复用的产品信息框架系统"迭代：HTML 单文件应用从 v1（产品库 + 6步培训进度）→ v2（localStorage 持久化 + 6步可点击）→ v3（一键导出发送）。16:01 插入一段无关主题：用户运行 `fusion-control-comp` 的 PPO 训练，AI 分析训练日志排障。

**这段对话厉害在哪：** 用户做了两件事充分体现她的产品思维：
1. **拒绝一次性答案，要可复用系统**——"每个产品的框架可以串联在一个系统里"这句话定义了需求边界：不是给一份说明书，而是建一座工厂，以后每上架一个新商品都走同一条流水线；
2. **提出"要发给各个销售"**——系统必须能脱离创建者独立运行，这直接催生了"导出为 HTML 文件"的设计（数据打包进文件本身，零依赖零服务器）。

**一句话概括：** 从"教销售上架一个商品"到"给销售一套可复用的产品上架系统"——用户把一次性的教学任务，做成了可持续复制的产品。

## 二、直觉捕获层

**触发源：** 用户招募了第一个销售，需要把"如何上架商品"这种个人经验**制度化**。她的直觉是：经验如果不能结构化、不能复制、不能脱离本人存在，就不是资产。

**关键瞬间 ① —— "只要框架"：**
> "你可能没明白我的意思，既然是个系统，你只需要给我框架即可，细节消息你不必提供，我自己填写，然后每个产品的框架可以串联在一个系统里"

这句话同时包含了三层指令：**只要框架**（拒绝信息过载）、**我自己填**（她掌控内容）、**串联成系统**（产品间可切换复用）。AI 从这一步才开始真正对齐。

**关键瞬间 ② —— 复制性焦虑：**
> "那咋办，我这个到时候完善好，要发给各个销售的"

localStorage 存在本地浏览器的现实一摆出来，用户立刻意识到系统的生死线是**可分发**。这推动了三方案对比（导出HTML / 导出JSON / 部署服务器），最终选择最零门槛的方案一。

**关键瞬间 ③ —— 升级兼容性担忧：**
> "新加的功能影不影响之前的填写"

用户对"已填数据的资产安全"极度敏感——这和她订单自动化项目里"源文件归档改名"、SKILL.md 的"单一真源"思维一脉相承：**数据是资产，工具可以换，数据不能丢**。

**方法论前奏：** 当天 22:08 用户提出"系统架构式的交互非常有用，聊天可以串联，像大树分支，把 HTML 直接发给 AI 就能瞬间明白"——这是当晚以及 6月30日 整个"外脑接口 / 直觉转译框架"探索的起点，详见第16篇归档。本段只记录触发时刻。

## 三、解剖转译层

### 产品上架完整要素（魔术臂章定制）

**标题优化逻辑：** 原标题 22 字，淘宝上限 30 字，关键词覆盖不足。三方案：
- 方案A（搜索覆盖广）：魔术臂章定制国家电网建筑应急救援山东吉林河北绣字订做（28字）
- 方案B（精准流量型）：国家电网山东吉林河北建筑应急救援魔术臂章定制绣字印字（28字）
- 方案C（批量采购型）：魔术臂章定制绣字国家电网建筑应急救援臂章订做小批量（27字）
- 优化逻辑：补充"绣字""印字""订做""小批量"等高频搜索词

**SKU 双维度设置：**
- 维度一（定制内容/款式）：国家电网通用款 / 山东·吉林·河北各电网专属款 / 建筑施工款 / 应急救援款 / 全自定义款
- 维度二（数量阶梯价）：1件 35元 → 10件 22元 → 50件 14元 → 100件 10元 → 500件以上联系客服；参考毛利率 40%~60%

**宝贝属性：** 类目=工作服/劳保用品→臂章/袖标；材质=魔术贴+精纺织物；工艺=电脑刺绣/热转印；标准尺寸 8×5cm；常见颜色藏青/黑/红；1件起订

**FAQ 七问：** 定制文字logo / 最低起订量 / 先看样品 / 效果一致性（确认稿后生产）/ 质量与掉色 / 开票 / 不满意处理

**发货时效阶梯：** 现货1工作日 → 定制3-5工作日 → 批量5-7 → 大批量7-10；买家长时间未回复确认稿，顺延并催促

**主图5张+详情图结构：** 白底图 / 工艺特写 / 穿戴场景 / 多款式排列 / 定制流程图；详情=Banner→卖点→工艺→尺寸→材质→定制流程→质量→FAQ→发货

> 注意：这些要素后来全部抽象成了 HTML 系统里"5个标签页"的字段框架——**指南本身没有被复用，指南的结构被复用了**。

### HTML 系统迭代三部曲

**v1 —— 框架第一版：**
- 左侧边栏两块：培训进度（6步流程）+ 产品库（"＋新增"不断添加，共用同一套框架模板）
- 右侧主区域 5 个标签页，字段全空白待填：基本信息 / SKU&定价 / 图片素材 / 常见问题 / 发货说明
- 局限：数据存页面内存，刷新即丢

**v2 —— 持久化 + 全步骤可点：**
- localStorage 持久化，右上角"✓ 已保存"提示，刷新不丢
- 6 个步骤全部可点击，每步独立框架：1开通店铺(清单) / 2上架商品(当前) / 3装修规划 / 4推广计划 / 5客服话术 / 6数据指标
- 数据 KEY 保持 `taobao_system_v2` 不变——这是后续升级不丢数据的关键设计

**v3 —— 导出发送：**
- 方案对比：①导出HTML（推荐，数据打包进文件，一个文件搞定零服务器）②导出JSON+导入（多人协作）③部署服务器（需要技术，成本高）
- 自动下载 `销售培训手册_2026-05-21.html`，微信/钉钉/邮件可发，销售双击打开数据已在
- 升级兼容保证：STORAGE_KEY 不变 → 打开新文件自动读取旧数据

### PPO 训练日志排障（fusion-control-comp）

**问题一：FPS = 1（最严重）**
- 4096 步耗时 3202 秒（约53分钟），每个环境 step 约 1 秒
- 常见原因：仿真环境本身重（物理/等离子体求解器）、环境未向量化并行、Python 与 C++ 之间大量数据拷贝
- 解法：`make_vec_env(YourEnv, n_envs=8, vec_env_cls=SubprocVecEnv)` 理论提升 8 倍

**问题二：奖励几乎不改善**
- 4 次迭代 ep_rew_mean 仅从 -17.1 → -16.9，几乎停滞
- 指标诊断：`std=1.0` 策略完全没收敛（还在随机探索）；`entropy_loss=-17.1` 动作空间极大（熵约 e^17≈2400万）；`explained_variance=0.16` 价值函数还非常差；`value_loss` 279→179 在慢慢学但太慢
- 超参建议：`n_steps=2048、batch_size=256、n_epochs=10-20、learning_rate=3e-4→1e-3、normalize_advantage=True、vf_coef=0.5、ent_coef=0.01`
- 排查清单：观测归一化（VecNormalize `norm_obs=True, norm_reward=True, clip_obs=10.0`）、奖励量级 scale 到 [-1,1]、动作空间维度

> 这段排障恰好是用户后来提出的"**竞赛实验型**"对话类型的真实样例（第16篇）——baseline 记录、优化方向尝试、失败归因、当前最优方案，一个不差。

## 四、编码师接口层

> 写给"下一步可执行"看的。

**销售系统可直接照做的部分：**
- 单文件 HTML 应用三要素：数据层（localStorage + 统一 STORAGE_KEY）+ 结构层（产品库数组 + 6步培训数据）+ 导出层（把序列化数据嵌进模板 HTML）
- 升级规则：**永远不要改 STORAGE_KEY**，新版本兼容旧数据靠它
- 分发方案选择矩阵：单人用 → localStorage；多人各自填 → 导出HTML（数据内嵌）；多人共享一份 → 服务器部署

**PPO 排障可复用的诊断流程：**
1. 先看 `fps` 和 `time_elapsed` → 环境效率问题优先解决（向量化）
2. 再看 `std` 是否长期为 1.0 → 未收敛信号
3. `entropy_loss` 绝对值大 → 动作空间大 / 探索熵高
4. `explained_variance` 低 → 价值函数差，reward 还没被理解
5. `value_loss` 下降但 ep_rew 不升 → 学习在发生但策略没获益，查奖励设计

**可延伸的问题：**
- 销售培训系统的下一步：导出后销售能否回传数据（成绩/完成度）？需要反向导入机制
- 6步培训流程的数据指标步——销售是否在用数据做复盘？（对应"数据指标"表单的深化）
- PPO 奖励 -17 不改善的根治：是环境稀疏奖励还是动作维度问题？需要看环境代码才能定论
- fusion-control-comp 这个项目与用户"AI技能比赛"主线的关系（她提到过参加技能比赛尝试不同 baseline）

### 关键洞见

1. **用户的产品思维：拒绝一次性答案，要可复用系统**——"框架可串联"的定义直接决定技术方案（产品库数组 + 统一模板）

3. **数据资产安全的直觉**——"升级影不影响已填数据" → STORAGE_KEY 不变的向后兼容设计。这与她订单自动化项目里"源文件归档改名""SKILL 单一真源"完全同构：**工具可迭代，数据不丢失**

5. **PPO 排障是"竞赛实验型"对话的原型**——baseline/尝试/归因/最优方案的完整循环，为第16篇的框架设计提供了真实案例
