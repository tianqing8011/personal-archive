## 三、解剖转译层

### 1. 工具概念澄清（POE vs Claude vs VSCode vs API）

| 工具 | 是什么 | 适合什么 | 不适合什么 |
|---|---|---|---|
| **POE** | AI 聊天平台，汇聚多个模型（含 Claude） | 日常问答、创意写作、临时性帮助 | 专业编程环境、规则化重复任务 |
| **Claude** | AI 模型本身，可通过多个平台访问 | 自然语言理解、解释概念 | 单独使用时没有"记忆保险" |
| **VSCode** | 专业代码编辑器（不是 AI 工具） | 写、测、调试代码 | 本身没有任何 AI 能力 |
| **API** | 程序调用 AI 的接口 | 自动化、批处理、定制应用、集成进自己系统 | 需要编程或低代码平台配合 |

**API 的核心优势：** 自动化（集成进自己的应用）、批量处理（一次处理大量数据）、定制化（按需构建）、灵活性（各种场景复用）。

**对用户最关键的一句：** POE 是"和 AI 聊天"的平台，API 是"让程序替你调用 AI"的通道——前者需要人每次在场，后者可以独立工作。

### 2. 用户业务与订单处理规则（本归档最核心的资产）

**业务背景：**
- 数据源：微信群"下单记录群"，每天产生大量订单
- 订单类型：**现货订单**（当天可发）与**定制订单**（含姓名定制，需单独记录在订货清单）
- 产品：消防装备与服饰类（领章、队旗、金盾、飞机、城市标、臂章、姓名牌、袖标等）

**姓名分类体系：**
- **金属/铁姓名**：金属铭牌类定制
- **布姓名（软姓名）**：软名牌、普通姓名定制 —— 注意：**软姓名属于布姓名**（首轮测试的纠正点）

**电话格式规则：**
```
原始： 付X[5474] 19597480981
转换： 姓名栏 = 付X
       手机号栏 = 19597480981-5474   （[代码] 变 "-代码"）
```

**地址规则：**
- 地址只到县级/镇级时，备注末尾加"**到了打电话**"（地址无法被快递系统精确解析）
- 完整地址（街道/门牌）无需添加

**定制订单判断标准：**
- 包含"姓名X个"
- 包含"具体人名+数量"（如"李国明 2"）
- 订单以人名列表开始
- 提到定制、刺绣等关键词

**信息关联原则：**
- 每条原始信息视为一个完整订单，备注信息必须与对应订单关联
- 同一条消息可能包含多个订单，需仔细切分
- 定制订单和现货订单必须严格区分

### 3. 四表方案（对话最终定稿）

| 表格 | 格式 | 内容 |
|---|---|---|
| **表1 所有订单** | 9 列固定 | 全部订单，含定制与现货 |
| **表2 定制内容表** | 定制专属 | 只显示定制内容：金属/铁姓名、布/软姓名、号码牌定制等 |
| **表3 当日现货发货表** | 同表1 | 剔除定制订单，仅现货 |
| **表4 定制订单表** | 同表1 | 只展示定制订单 |

**表1/3/4 的 9 列固定格式：**
`收件人 | 手机号 | 收货地址 | 平台订单号 | 商品信息 | 规格信息 | 数量 | 重量 | 备注`
- **平台订单号、商品信息、规格信息、数量、重量 5 列保持空白**
- **所有产品信息统一写在备注栏**，要简洁

### 4. AI 记忆局限与应对方案（诚实讨论）

AI 坦诚承认：对话过长时早期细节可能"淡出"活跃记忆。给出的实用方案：
- 每个批次用新会话，开场附一段简短的规则提醒
- 创建"关键规则文档"可随时复制粘贴
- 出错了直接指出，当场纠正
- **最可靠方案：把规则写进代码**——代码不会遗忘

> 这句总结很关键：**"人机协作模式实际上比完全依赖自动化工具更可靠"**——但前提是规则被显式定义。

### 5. Cursor：从诞生到"为什么大家都在说它"

**发展历程：**
- 2022年底~2023年初：Michael Truell、Anton Cao 创立，YC 出身，约 1500 万美元种子轮（a16z 参与）
- 早期是 VS Code 扩展 → 发展为集成 GPT 的独立编辑器
- 2023年3月：测试版发布；2023下半年：用户快速增长
- 2024年：团队协作、自托管等高级功能；2024年11月：再次融资，估值大幅提升

**核心优势：** 将 AI 深度集成进编辑器，能理解**整个代码库上下文**——这是它区别于 GitHub Copilot 的关键。

**对代码小白的价值：**
- 选中陌生代码 → 让 AI 解释作用与原理
- 自然语言描述需求 → AI 生成完整代码
- 报错 → AI 看懂错误并给出修复建议+解释
- 学习辅助：简化概念、生成练习、指导最佳实践

**为什么大家都在说它：** 效率提升大、降低编程门槛、对话式编程创新交互、开发者口碑传播、支持几乎所有语言。

**未来形式（AI 预测）：** 更深代码理解（架构级重构）、开发流程整合（CI/CD 全流程）、多模态（草图直接生成界面）、团队协作增强、个性化编程教练、从"被动响应"到"主动提议"的自主助手。

### 6. 为什么 Cursor 更适合"固定规则高频任务"

| 维度 | 对话式 AI（Claude） | 脚本自动化（Cursor 辅助开发） |
|---|---|---|
| 规则记忆 | 可能遗忘、需反复提醒 | **代码持久化，永不遗忘** |
| 每次成本 | 每次都要粘贴+可能纠正 | 一次编写，反复使用 |
| 批处理 | 受限于对话长度 | 可批量处理大量订单 |
| 灵活性 | 格式多变时灵活 | 规则变化时改代码即可 |
| 门槛 | 零门槛 | 需要一次性的学习投入 |

**结论：** 规则固定、高频重复 → 自动化更优；偶尔、格式多变 → 对话更灵活。**最佳组合：脚本处理标准格式，对话处理异常情况。**

## 四、编码师接口层

> 这一层记录"可以照做"的操作步骤。

### 1. Cursor 安装与初始设置（用户实际走的流程）

- 官网下载安装 → 创建/登录账号
- **快捷键配置**：选 "VS Code"（最通用，用户不熟也推荐默认）
- **聊天语言**：选中文（只影响对话，界面仍为英文——界面暂不支持中文本地化，属正常现象）
- **终端集成**：点击 Install（可选但推荐）
- **布局**：选 **IDE 布局**（更专注文件与代码，适合脚本工作流）
- **主题**：选 Dark（护眼，代码高亮对比度好）

### 2. POE API key 能不能填进 Cursor？——不能直接填

POE 的 API key 与 OpenAI API key 是两套体系，Cursor 设置里不会识别 POE 的 key。**正确做法：直接用 Cursor 内置激活的模型**（如 Opus 4.5、GPT-5.1 Codex Max），无需额外配置。

### 3. 创建订单处理脚本的路径

```
新建项目文件夹（如"订单整理自动化"）→ 新建 order_processor.py
→ 在 Cursor 聊天框描述需求 → AI 生成代码 → 存入文件
→ 准备 requirements.txt（pandas + openpyxl）→ pip install
→ 准备测试 Excel → 运行 → 检查结果 → 迭代改进
```

### 4. 四表脚本的核心逻辑（AI 提供的结构）

```python
import pandas as pd
# 读取Excel
# 表1：所有订单，9列固定，后5列留空，电话[代码]→-代码
# 表2：定制内容表（金属/铁姓名、布/软姓名、号码牌）
# 表3：现货订单 = 所有订单 − 定制订单
# 表4：定制订单 = 按定制关键词筛选
# 地址到县级/镇级 → 备注追加"。到了打电话"
# 保存为 处理结果.xlsx（多 sheet 或独立文件）
# 用 tkinter.filedialog 弹窗选择文件，方便小白使用
```

### 5. 每日工作流建议

- 每批订单用新会话；开场粘贴规则提醒或调用脚本
- 直接指出任何不符合预期的细节（哪怕是小的）
- 规则变化时明确告知："从今天开始我们需要调整…"
